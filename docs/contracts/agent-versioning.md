# AgentSpec 版本语义 v1

> 定义 Agent 定义的不可变性、版本递增、软删除与任务侧版本锁定。

## 1. 不可变版本

- 每个 `(agent_id, version)` 对应的 AgentSpec **一经创建不可修改**
- `PUT /api/v1/agents/:id` 不修改旧版本，而是创建 `version + 1` 的新版本
- 版本号从 1 开始，**单调递增**，无空洞（不做 git 式哈希，运维可读）
- 创建时允许提交完整 spec + `base_version`（乐观锁：若 base 已落后则拒绝，防并发覆盖）

## 2. 任务侧版本锁定

- Task 创建时记录 `agent_id + agent_version`，**执行时按锁定版本路由**
- Agent 更新不影响已存在任务（排队时 v3、执行时已是 v5 → 仍按 v3 执行）

## 3. 删除

- `DELETE /api/v1/agents/:id` 为**软删除**：标记 `deleted_at`
- 删除后：新任务提交被拒（`INVALID_PAYLOAD`），存量任务继续执行完
- v1 不提供恢复 API，但存储层保留 `deleted_at` 字段使恢复成为可能

## 4. 实现要求

| 阶段 | 原子递增实现 |
|---|---|
| M1（内存） | 互斥锁保护 map |
| M2（Redis） | Lua 脚本原子 `GET + INCR`（见下方理由） |

**为什么 Redis 版必须用 Lua？** "读当前版本 → 写新版本"是两条命令，非原子；并发更新时两个写入者可能拿到同一版本号，造成版本冲突且难以察觉。Lua 脚本在 Redis 单线程内原子执行，是分布式场景下的标准解法（等价于数据库的 `UPDATE ... SET v=v+1 RETURNING`）。

## 5. 设计理由（面试要点）

**为什么版本不可变？**
任务可复现/可回放的前提。排查"上周三那个任务为什么答错"时，能精确还原当时的 Agent 定义（模型参数、工具集、提示词），而不是被后续更新覆盖后的"现在的样子"。

**为什么执行时锁定版本？**
消除"排队时 A 版本、执行时 B 版本"的语义漂移。任务结果是 `(payload, agent_version)` 的确定函数，版本锁定让这个函数可推理、可对比（A/B 测试也依赖这一点）。
